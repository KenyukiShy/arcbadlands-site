# Architectural Refactoring Plan for `tracker-crm.html`

**Date**: 2026-08-02
**Author**: AI Assistant
**Context**: This plan analyzes `tracker-crm.html` to identify opportunities for applying common design patterns and improving code structure. The file `board.html` was not present in the repository and is not included in this analysis.

## Executive Summary

The `tracker-crm.html` file contains a large, monolithic `<script>` block that mixes application logic, configuration, and data access. The most beneficial refactoring is to **separate concerns** by splitting this script into dedicated files.

- **Adopt ✅ Repository Pattern**: Centralize all API calls into a new `assets/tracker-repository.js` file.
- **Adopt ✅ Domain/Config/Data Separation**: Move static configuration into `assets/tracker-config.js` and data access into `assets/tracker-repository.js`, leaving `tracker-crm.html` with primarily application/domain logic.
- **Defer ❌ Observer Pattern**: The current manual re-render flow is simple and sufficient. A full observer implementation would add unnecessary complexity.
- **Defer ❌ Strategy Pattern**: The existing `hasRole()` helper function is a clean and adequate solution for the application's simple permission checks.

## 1. Repository Pattern: Adopt ✅

### Analysis
The script in `tracker-crm.html` makes numerous direct `fetch` calls to the backend API from various functions. This scatters data access logic, making it hard to manage headers, endpoints, and error handling consistently.

- **Files/Functions Affected**:
  - `tracker-crm.html`: `bootstrapTrackerKey`, `window.storage` shim, `loadEngagements`, `logAuditEvent`, `loadContacts`, `submitFlag`, `handleAuthChange`, `authRequestBtn.onclick`, `loadItinerary`, `connectMyCalendar`.

### Proposal
Create a new file, `assets/tracker-repository.js`, to serve as a dedicated data access layer (Repository). This module will encapsulate all `fetch` calls and expose a clean, high-level API to the rest of the application.

### Implementation Plan

1.  **Create `assets/tracker-repository.js`** to house a `TrackerRepository` object. This object will manage the API base URL, the `TRACKER_KEY`, and the user's ID token internally.

    ```javascript
    // assets/tracker-repository.js (conceptual)
    const TrackerRepository = {
      _apiBase: "",
      _trackerKey: null,
      _idToken: null,

      async init(apiBase) { /* ... fetches client key ... */ },
      setToken(token) { this._idToken = token; },

      getEngagements: async () => { /* ... fetch /engagements ... */ },
      getState: async (key) => { /* ... fetch /tracker-storage/{key} ... */ },
      saveState: async (key, value) => { /* ... POST /tracker-storage/{key} ... */ },
      getVendorContacts: async () => { /* ... fetch /vendor-contacts ... */ },
      getMe: async () => { /* ... fetch /me ... */ },
      // ... other methods for audit logs, flagging, etc.
    };
    ```

2.  **Refactor `tracker-crm.html`** to use the new repository.

    - **Before (in `tracker-crm.html`)**:
      ```javascript
      // lines 1030-1050
      async function loadEngagements(){
        // ...
        const res = await fetch(`${TRACKER_API_BASE}/engagements`, {
          headers: {
            "X-Tracker-Key": TRACKER_KEY,
            "Authorization": `Bearer ${idToken}`
          }
        });
        // ...
      }
      ```

    - **After (in `tracker-crm.html`)**:
      ```javascript
      // assets/tracker-repository.js would be created.
      // tracker-crm.html would be modified:

        // ...
        const data = await TrackerRepository.getEngagements();
        // ...
      }
      ```

## 2. Domain/Config/Data Separation: Adopt ✅

### Analysis
The file `tracker-crm.html` contains over 1000 lines of JavaScript where static configuration (`VEHICLE_CARDS`, `STAGES`) is mixed with application logic (`renderAll`, `buildCard`) and data fetching (`loadState`, `loadEngagements`).

### Proposal
Decompose the monolithic script into logical, separate files for better organization and maintainability.

### Implementation Plan

1.  **Create `assets/tracker-config.js` for static configuration.**
    - **Action**: Move all constant, static data structures from `tracker-crm.html` into this new file.
    - **Files/Functions/Line Ranges Affected**:
      - `tracker-crm.html`, lines `1000-1203`: Move the definitions of `PEOPLE`, `STAGES`, `STAGE_CLASS`, `FOLLOWUP_TYPES`, `VEHICLE_CARDS`, `REGION_INTRO`, `ND_CATS`, and `GA_CATS`.

2.  **Use `assets/tracker-repository.js` for data access.**
    - **Action**: As detailed in the Repository Pattern section, this file will consolidate all `fetch` calls.

3.  **Simplify `tracker-crm.html` to focus on domain logic.**
    - **Action**: The main `<script>` block will be significantly smaller. It will import the config and repository modules and contain the core application logic (state management, rendering, and event handling).
    - **Example Structure**:
      ```html
      <!-- tracker-crm.html -->
      ...
      <script src="assets/tracker-config.js"></script>
      <script src="assets/tracker-repository.js"></script>
      <script>
        // Core application/domain logic remains here
        // (e.g., renderAll, buildCard, event handlers)
        // but now calls TrackerRepository for data and uses
        // variables from tracker-config.js.
      </script>
      </body>
      </html>
      ```

## 3. Observer Pattern: Defer ❌

### Analysis
The application state is updated through direct user actions, and UI re-rendering is handled by explicit function calls (e.g., `renderAll()`, `saveState()`). The only true observer is `window.ArcAuth.onAuthChange()`, which is provided by an external library and used correctly to react to authentication events.

### Proposal
**Do not implement a custom Observer pattern for application state.**

### Justification
The current data flow is simple and easy to follow. Introducing an observable state object with publishers and subscribers would add significant complexity for little practical benefit, as there is no requirement to react to background data changes. The existing pattern of "change state -> save state -> re-render" is sufficient.

## 4. Strategy Pattern: Defer ❌

### Analysis
Permissions are checked using the `hasRole(roles, role)` helper function. This function is used in a few places to conditionally render UI elements (e.g., the "Flag for moderation" button).

- **Files/Functions Affected**:
  - `tracker-crm.html`: `hasRole`, `hasAnyAppRole`, `applyRoleNav`, `buildCard`.

### Proposal
**Do not refactor the permission logic into a formal Strategy pattern.**

### Justification
The current `hasRole()` function is already a clean, centralized, and reusable solution for the application's simple permission needs. A formal Strategy pattern, with separate objects/classes for each permission check, would be an unnecessary abstraction that would likely decrease readability for what is currently a straightforward boolean check.
